Bottom line, up front

The gates worked. The one thing they couldn't test was whether Legion could actually talk to UDL.

Across this engagement, ten App Store stages went green, coverage sat near 96%, and 608 tests passed, while /udl/elset answered HTTP 400 to every single call the application had ever made to it, since the first version. Nothing in the pipeline could catch that, because nothing in the pipeline calls the real Unified Data Library (UDL). It surfaced only when Ash ran a real deployment and pasted back what UDL actually said. That is the headline lesson below, and almost everything else in this document is a variation on the same root cause: a check that reports confidently on something it never actually observed.

Headline finding

A green pipeline said nothing about whether the feature worked

This is worth sitting with before anything else in this document, because it is the one finding that outweighs the rest combined.

⚠

Every chart and the entire belt were non-functional from the first version

src/udl_client.py called /udl/elset with satNo alone. Ash confirmed against live UDL on 14 September 2026 that the endpoint requires an epoch qualifier and answers HTTP 400 without one. That means the single UDL call every family movement chart and the entire GEO belt depend on had never once succeeded, for the whole life of the project, through every version that shipped with “96% coverage, live smoke-tested” written beside it. It was not a credentials problem, not an egress problem, and not the endpoint being wrong. It was a malformed query the test suite could never catch, because the test suite talks to a fake UDL client that answers whatever it is told to answer.

Two things made this worse before Ash's live diagnostics broke it open. First, get_elset took payload[0] on the unconfirmed assumption that UDL returns its newest record first, an assumption that had never been tested against real UDL because real UDL had never answered. Second, the application's own udl_diagnostics.py module, built specifically to tell a future reader what UDL actually said, hard-coded "http_status": 200 on its success path and let a swallowed 4xx read as “not available here, which is expected.” A tool built to end guessing was itself guessing, silently, in the one place a reader had no other way to check.

✓

What good process discipline actually bought here

The FACT / INFERENCE / SPECULATION discipline this codebase already holds itself to is exactly why this was recoverable in one sitting rather than a mystery. Every UDL-derived value in the codebase was already marked as fact or inference in its docstring before this happened. When the inference turned out to be wrong, there was a named, searchable list of everywhere it was relied on. That discipline is worth protecting more than any single fix in this document.

The core pattern

“A test that passes because it never looked”

This phrase already appears in this codebase's own test comments more than once, independently, because the same failure mode kept recurring. It is worth naming as the single pattern behind most of what follows, rather than treating each instance as an unrelated one-off.

this session

The diagnostics module fabricated its own evidence

_probe hard-coded "http_status": 200 on every success path, and get_elset_history swallowed a 4xx into a silent None. Together they produced a report that read as settled fact when nothing had actually been observed. The module had no test file at all, and 56% coverage, which is how it survived.

recorded in CLAUDE.md

The audit trail was silent for the life of the project

Every test that covered logging asserted through caplog, which installs its own root handler. The trail appeared to work under test and only under test, because nothing had configured a real handler in the running application.

recorded in CLAUDE.md

Three ranking guards read the wrong layer entirely

Two asserted against an API whose response_model had already stripped the field under test. One read a 400 error body and found no ranking in it, correctly, for the wrong reason: the endpoint had rejected the request before ranking logic ever ran.

recorded in CLAUDE.md

A migration idempotency test compared a file with itself

It compared the store file before and after a read, and a read migrates only in memory without writing. Calling the public migration function twice also passed, because the schema-version guard made the second call a no-op. Only calling the layer builder directly, twice, caught the sabotage.

found in browser

svgEl was declared twice

A redeclaration throws at parse time and kills the whole module script. Every panel came up blank in a real browser while all 66 contract tests passed, because every one of them read the markup rather than running it.

recorded in CLAUDE.md

Three data shapes were guessed wrong, all in one new module

Object claims assumed non-empty when claims are analyst-created and start empty; the segment collection assumed to be segments when it is pol_segments; TBC assumed to be a marker when it is a source_class. Any one of the three would have shipped a queue that was silently, permanently empty.

What already works

The safeguards already in place, and why they earned their keep

  • The rule register. docs/SONAR-RULE-REGISTER.md turned three failed uploads into a pass by writing down every Sonar rule the platform had actually fired, rather than guessing at what it might fire next. This is the difference between a reactive fix and a standing defence.
  • The calibration discipline. Every new guard in this session was proven by breaking the thing it protects on purpose, first, and confirming the guard names the exact defect before it was ever trusted. This is what caught the fabricated 200 and the wrapper-swallowed 4xx, both, the moment they were introduced as tests rather than assumed safe.
  • The refusal scripts. bump_version.sh and package.sh now refuse to ship a release that would land in an unmeasurable-coverage state, rather than warning about it in text that can be missed. A condition no retry can clear should not be possible to ship by accident.
  • FACT / INFERENCE / SPECULATION discipline. The single reason the epoch defect was fixed in one sitting rather than a multi-day hunt: every place the wrong assumption was relied on was already named in a docstring as an inference, not stated as settled.
  • Archive, never delete. Applied consistently to systems, claims, segments and assessments. A withdrawn or corrected entry stays visible rather than leaving a silent gap nobody notices.
Do & don't

What this session's record actually argues for

Do

✓Calibrate every new test or guard by deliberately breaking the thing it protects, before trusting it green.
✓Read the full, untailed output of a gate or test run before reporting it passed. Piping through tail hid the one warning that would have prevented a wasted upload cycle.
✓Verify a data shape against the real store or API before writing code against it, every time, not only when told to.
✓Treat a hard-coded status, count, or observation found in one module as a reason to search for the same shape everywhere else.
✓Ask what property an old shape was providing by accident before applying a mechanical fix across a codebase. The async-to-sync route handler change nearly removed the thing serialising the store's writes.
✓Ship a test file with any new module before it ships, not after. Zero test files is what let the fabricated status survive.

Don't

✗Don't call a test result “verified” when it read a Pydantic response_model, an error body, or a caplog capture. All three have hidden something real here.
✗Don't let a green pipeline and a high coverage number stand in for the feature actually working against the live external system it depends on.
✗Don't rename or introduce a token, constant, or CSS custom property without checking for an existing use of that exact name. The spacing scale silently overwrote five validated series colours this way.
✗Don't read “the gate passed” and “the feature works” as the same claim. They answer different questions and this session's headline finding is the gap between them.
✗Don't fold a fallback path (a chart surviving a 4xx) and a diagnostic path (reporting what actually happened) into the same function. One needs to recover; the other needs to tell the truth.
Recommendations

What to put in place, in priority order

1

Resolve the tag-push failure on the GitHub remote

Every version this session tagged locally, none of them pushed: git push --tags returns HTTP 403 and the remote holds zero tags. scripts/package.sh builds a release from its tag, so a fresh clone of this repository cannot currently reproduce a single shipped version. This is a live gap, not a historical one, and it needs a repository administrator to check branch or tag protection rules on the GitHub side.

githubblocking
2

Schedule a recurring live UDL check, now that a path to run one exists

scripts/udl_live_check.py can now settle real questions against real UDL, and the notification window_hours semantics are still open. Left reactive, the next silent break could sit undiscovered as long as the epoch defect did. A monthly run, even manual, converts this from “whenever someone happens to deploy and look” into a standing check.

processudl
3

Add a standing rule: no diagnostic or observability module ships without a test file

src/udl_diagnostics.py is the one module whose entire purpose is telling a reader what actually happened, and it had 56% coverage and no test file. That is precisely backwards: a module that reports on other failures should be held to a higher bar than the code it reports on, not a lower one. Worth a line in CLAUDE.md's standing instructions, and worth a coverage floor specifically for any module matching *diagnostic* or *probe* in check-quality-gate.sh.

codegate
4

Write the calibration rule down as a named, general standing instruction

It already appears correctly, repeatedly, as a lesson learned after each specific incident. It has never appeared as a rule stated once, in general, ahead of the next incident. A single line in CLAUDE.md's standing instructions: “A new test or guard is not trusted until it has been shown to fail, by name, against the defect it targets, restored on purpose.”

memorylow-risk
5

Grep for the fabricated-value shape across the rest of the codebase

The 200 status was found once, by chance, while chasing a different question. It is worth one deliberate pass across src/ for any other place a status, count, or timestamp is assigned a literal value rather than read from an actual observation, particularly in src/orbits.py and src/family_elements.py, which share the same UDL boundary.

auditcode
6

Keep asking for the untailed, full output before accepting “done”

This is a safeguard against the assistant's own failure mode more than a process gap on your side. A standing habit, stated once, of asking “show me the whole gate output, not a summary” before closing an item costs nothing and would have caught the piped-through-tail mistake immediately rather than after it had already cost a missed warning.

Where more would have helped

An honest look at the other side of this

ⓘ

The single highest-value action in this whole engagement was Ash's, not the assistant's

Pasting the real diagnostics output, unprompted, with an explicit “make no changes yet,” is exactly the right move and is the reason the epoch defect is now closed rather than still latent. That is not a gap to fill. It is worth naming as the pattern to repeat: real evidence from a real running system, handed over before any fix is attempted, beats any amount of local testing against a fake client.

Two things are fair to name as places where more would genuinely have helped, stated plainly rather than as criticism, since the record does not support anything stronger:

  • Live UDL access came late in the project's life, and that was a policy constraint, not a choice. The organisation's egress policy blocked unifieddatalibrary.com from this development environment for most of the project. Nothing in this session's record suggests that could have been resolved sooner by working differently here. Once access existed, it was used immediately and well. The lesson is forward-looking rather than a fault to correct: now that the path exists, using it on a schedule (recommendation 2) turns this from a one-off discovery into a standing check.
  • A second, independent read of the diagnostics report's own wording might have caught the fabricated 200 sooner. “Not available at this path, which is expected” reads as settled. It was written by the same tool that turned out to be wrong. Asking “what did the tool actually observe versus what did it conclude” as a standing question, whenever a report states something as expected or normal, is a cheap habit that would have surfaced this a step earlier. This is offered as something to ask of any report the assistant produces in future, not specific to this one.
